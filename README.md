# zoho-auto-tasks

An OpenCode agent that turns an informal daily work summary into professional Zoho Desk
task records.

You write what you did. It drafts one task per distinct work item, validates everything
locally, shows you a preview, and creates the tasks in Zoho Desk — reporting exactly what
happened to each one.

It will not invent accomplishments, deadlines, or client associations. When work-session
scheduling is configured, durations are explicitly synthetic estimates and clock times are
allocated deterministically.

---

## Status

The core is built, tested, and verified against a live Zoho Desk tenant. New users configure
their own tenant through `.env`; setup resolves their email and department to Zoho IDs rather
than requiring manual JSON editing. See [Setup](#setup).

Verified API behaviour and its sources are in [docs/zoho-field-map.md](docs/zoho-field-map.md).
Design decisions and their rationale are in [plan.md](plan.md), section 24.

## Requirements

- Node.js 22.18 or newer (for native TypeScript execution and `node:sqlite`)
- OpenCode 1.18 or newer
- A Zoho Desk account with permission to create tasks

There is no build step. TypeScript runs directly under both Node and OpenCode's embedded
Bun runtime.

## Setup

For the abbreviated clone-to-first-task path, see [Quick Start](docs/quickstart.md).

### 1. Install dependencies and register the agent

```bash
npm install
npm run install-agent
```

This writes two files into `~/.config/opencode/` — `agents/daily-tasks.md` and
`tools/desk.ts` — backing up anything it would overwrite. It also creates
`~/.config/zoho-auto-tasks/.env` from a safe template when absent. `config.json` is generated
from that environment file by setup. It does not modify `opencode.json`.

### 2. Fill in `.env`

Edit `~/.config/zoho-auto-tasks/.env`:

```dotenv
ZOHO_REGION=us
ZOHO_TIMEZONE=Etc/UTC
ZOHO_OWNER_EMAIL=you@example.com
ZOHO_DEPARTMENT_NAME=Support
ZOHO_CLIENT_ID=...
ZOHO_CLIENT_SECRET=...
ZOHO_REFRESH_TOKEN=...
```

Use `ZOHO_DEPARTMENT_ID` instead of the name when you know it. If both are set, the ID wins.
For a token that can access multiple organizations, also set `ZOHO_ORG_ID`. The file is
created with mode `600`, is never copied into OpenCode, and is ignored by Git. `config.json`
is generated by setup and is not a user-managed file.

### 3. Create a refresh token, if needed

Use a **self-client**, which needs no redirect URI or web server.

1. Go to <https://api-console.zoho.com> and choose **Add Client → Self Client**.
2. Open the **Generate Code** tab and enter this scope string:

   ```
   Desk.activities.tasks.CREATE,Desk.activities.tasks.READ,Desk.search.READ,Desk.basic.READ,Desk.fields.READ,Desk.layouts.READ
   ```

3. Select your Desk portal and generate. **The code expires in about three minutes.**
4. Exchange the code for a refresh token, leaving `ZOHO_REFRESH_TOKEN` blank in `.env`:

   ```bash
   node src/cli.ts connect
   ```

    The client ID and secret from `.env` are available as defaults. The command exchanges the
    generated code and writes a restricted temporary credential store. The next `npm run setup`
    migrates those credentials into `.env`. The code is read from stdin, so it never lands in
    your shell history or the process list.

   Environment variables (`ZOHO_CLIENT_ID`, `ZOHO_CLIENT_SECRET`, `ZOHO_REFRESH_TOKEN`)
   work too and take precedence over the file. Never pass credentials as command-line
   arguments.

The refresh token does not expire, but it can be revoked. The short-lived access token is
cached at `~/.local/share/zoho-auto-tasks/token-cache.json` with mode 600, because Zoho
throttles token requests to ten per ten minutes.

### 4. Resolve your tenant configuration

```bash
npm run setup              # read-only discovery, then saves resolved IDs locally
node src/cli.ts doctor     # checks config and connectivity, writes nothing
```

`setup` finds the active agent matching `ZOHO_OWNER_EMAIL`, resolves the selected department,
infers supported status/priority values, migrates any existing local credentials into `.env`,
and saves the numeric IDs plus metadata cache in the restricted local configuration. It refuses missing or ambiguous users, departments, and
organizations instead of guessing. Run `node src/cli.ts setup --force` only when intentionally replacing an existing
derived configuration.

`discover` remains available to inspect a portal manually:

```bash
node src/cli.ts discover   # read-only: lists departments, agents, statuses, fields
```

It also tells you where the **work date** can go, which is a decision you must make: Zoho Desk
tasks have no work-date field.

| `workDate.mode` | Behaviour |
|---|---|
| `dueDate` | Sets `dueDate` to local noon on the work date. Sortable and filterable in Desk. |
| `customField` | Writes the date into a task custom field. Only used if the field is verified to exist. |
| `none` | The date appears only in the preview and local state. |

### 5. First live test

Do this once, deliberately, before daily use:

```bash
node src/cli.ts prepare examples/day.json
node src/cli.ts submit <batchId>
node src/cli.ts show <batchId>
```

Confirm in Zoho that the task looks right. In particular, check whether a task created
with the Completed status actually closes — Zoho does not document that, so the tool
verifies it by reading the task back and tells you if it stayed open.

## Daily use

In OpenCode, switch to the **daily-tasks** agent and write your day in plain language:

> Auditax: installed Ubuntu, deployed Nessus, ran vulnerability scans. Makana: troubleshot
> connection problems, still failing. Need to write the AI Studio report tomorrow.

The agent drafts the tasks, shows you a preview, and creates them once you approve. Set
`submissionMode` to `direct` to skip the approval step once you trust it.

## CLI

Every command is safe to re-run. Only `submit` writes to Zoho.

| Command | Purpose |
|---|---|
| `connect` | Guided one-time credential setup |
| `setup [--force]` | Resolve `.env` owner and department into a local tenant configuration |
| `doctor` | Check configuration, credentials and connectivity |
| `discover` | Read tenant metadata and cache it (read-only) |
| `prepare [file]` | Build and validate a batch from JSON, or stdin |
| `show <batchId>` | Show a batch, its state, and Zoho IDs |
| `submit <batchId>` | Create the ready items |
| `reconcile <batchId>` | Resolve uncertain items by searching Zoho |
| `confirm <itemId>` | Mark a duplicate-flagged item as distinct work |
| `purge` | Apply the raw-text retention policy |

## How it protects you

**It never invents facts.** The agent prompt forbids adding outcomes, durations, severity
or impact that you did not state. "Troubleshot X, still failing" stays unresolved.

**It never guesses an ID.** Departments, owners, statuses and priorities are validated
against what your portal actually has. An unknown client stays as text rather than being
attached to the wrong contact.

**It never replays an ambiguous write.** Zoho has no idempotency key, so a timeout after
sending a create is treated as *unknown*, not *failed*. The tool searches for the task
instead of creating a second one, and if it cannot decide, it says so and stops.

**It never loses a task ID.** The Zoho ID is persisted the moment it is returned, before
any verification step runs.

**It distinguishes created from verified.** "Created and verified" means the task was read
back from Zoho. "Created but read-back pending" means the ID exists but the fields are
unconfirmed. These are never conflated.

**It never leaks credentials.** The agent has no file, shell or network access, and no tool
returns a token. Errors are redacted before they reach a log or the model.

**It resists prompt injection.** Pasted text is data. An instruction hidden in a work
summary cannot change credentials, permissions, or submission behaviour.

## Testing

```bash
npm test            # Node
npm run test:bun    # exercises the Bun/bun:sqlite path OpenCode actually uses
```

The suite covers DST gaps and repeated hours in Asia/Beirut, payload validation, duplicate
detection, item claiming, crash recovery, error classification, credential redaction, and
the full submit/reconcile flow against a stubbed Zoho.

## Layout

```
src/config/     configuration, secrets, region allowlist
src/domain/     schemas, timezone handling, validation, fingerprints
src/zoho/       OAuth, transport, task and metadata operations
src/state/      SQLite store, item states, recovery, retention
src/service/    prepare, submit, reconcile
src/cli.ts      command line entry point
opencode/       agent definition and tool adapter
docs/           verified field map and operations runbook
```

The Zoho client is independent of OpenCode, so the same validation and recovery behaviour
can be reused by an MCP server or a hosted service later.
